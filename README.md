# Stock allocation for SAP

This repository contains a small, production-oriented ABAP stock-allocation service. It reads unrestricted-use stock from `MARD`, reads open sales requirements from `VBBE`, applies optional demand priorities from `ZSTOCKPRIO`, allocates stock with a selectable deterministic strategy, and persists the current plan in `ZSTOCKPLAN` and `ZSTOCKALLOC`.

## Design

The pure allocator has no SAP dependencies. Interfaces isolate reads, writes, locking, authorization, and audit logging, while SAP-specific adapters live at the edge. This makes the allocation rule ABAP Unit-testable and keeps standard tables read-only. The report `ZSTOCK_ALLOCATE` is the transaction boundary and commits the completed allocation run. Authorization is checked before locking or database access, a client/material/plant/storage-location SAP lock remains held until that commit, and each successful plan is written to the Business Application Log in the same logical unit of work. Two canonically ordered demand reads must match while bracketed by unchanged stock; an unstable snapshot is retried up to three times and continuous stock, requirement, or priority movement aborts before logging or persistence. Unrelated allocation scopes can run concurrently.

Allocation statuses are `F` (full), `P` (partial), and `N` (none). Quantities carry the material base unit read from `MARA`, the unit in which SAP manages material stock. Results retain the sales-order schedule-line key, so multiple requirements for one item cannot overwrite each other. Before any plan can be returned, logged, or persisted, an invariant gate verifies quantity arithmetic, statuses, row context, and total stock conservation. Re-running the report atomically replaces the `ZSTOCKPLAN` scope header and its `ZSTOCKALLOC` detail rows. The header preserves stock context, strategy, window, cardinality, audit provenance, and a monotonically increasing scope-local version even when a successful plan contains no demand rows. The same LUW appends an immutable versioned copy to `ZSTOCKPHIST` and `ZSTOCKAHIST`, retaining full historical evidence while current-table reads remain simple.

`P_RESRV` keeps a non-negative quantity of unrestricted stock outside the allocation pool. The buffer applies identically to simulation and committed execution, and its value is persisted and included in the application-log summary. If the buffer exceeds stock, allocatable stock is zero.

`P_FROM` and `P_CUTOF` optionally bound the planning window by material-availability date. Leave both blank to include every positive open requirement, set either boundary independently, or set both to read only `VBBE` schedule lines whose `MBDAT` falls inside the inclusive range. A start date after the cutoff is rejected before authorization, locking, or data access. The window applies identically to a selected strategy and to `P_COMP`, is pushed into the database query before priority enrichment, and is retained in plan rows, persisted snapshots, report output, and BAL summaries.

Priorities are optional signed integers stored as client-dependent application data in `ZSTOCKPRIO` for a material, plant, storage location, sales order, and item. Maintain them through report `ZSTOCK_PRIORITY`; its save and delete paths use the same allocation-scope lock, so configuration cannot change during an allocation run. Higher values allocate first. Equal priorities—including the default value zero—retain FIFO ordering, so existing behavior is unchanged when no configuration exists.

`P_STRAT` selects how constrained stock is distributed among demands with the same priority. `F` is strict FIFO by material-availability date and remains the default. `P` allocates proportionally to requested quantity. `E` applies max-min fair sharing: small demands are completed first, then the remaining stock is divided equally among larger demands. `S` serves the smallest demands first, maximizing the number of fully supplied schedule lines in the tier. `C` is complete-only FIFO: it skips requests that cannot be supplied completely and never creates partial shipments. If any demand in a priority tier remains incomplete under `C`, unused stock is held instead of passing to a lower tier. All strategies process higher-priority tiers first, use sales-order keys as deterministic tie breakers, conserve stock through three-decimal rounding, and never allocate more than requested. The effective code is shown in report output, persisted per allocation row, and recorded in the application-log summary.

Select `P_COMP` to compare all five policies in one side-effect-free run. The service establishes one stable stock/demand snapshot and calculates every candidate from it. The report displays full, partial, unallocated, and short demand counts, the earliest material-availability date affected by shortage, quantity fill percentage, complete-demand service-level percentage, stock-utilization percentage, normalized fulfillment fairness, allocated and shortage quantities, and unused allocatable stock for each strategy; comparison never locks, logs, persists, or commits.

`P_OBJ` controls the deterministic recommendation printed by comparison. `S` maximizes the number of completely supplied demand lines, then allocated quantity, then minimizes partial lines. `Q` maximizes allocated quantity, then completely supplied lines, then minimizes partial lines. `F` maximizes Jain's fairness index across each demand's fulfillment ratio, then allocated quantity, then completely supplied lines. `D` minimizes due-date urgency by preferring no shortages, then pushing the earliest shortage date later, reducing the affected-demand count, and reducing shortage quantity. Fairness is reported from 0 to 100; equal fulfillment ratios score 100, while concentrated allocation scores lower. Exact ties retain comparison order, making FIFO the stable primary recommendation when every outcome is equivalent, and the report lists every equally ranked strategy so planners can see that the choice is not unique. The recommendation is advisory; only a normal non-simulation run using `P_STRAT` persists a plan.

Simulation requires display activity `03` and committed execution requires activity `16`, together with the requested plant (`WERKS`) and storage location (`LGORT`), on authorization object `ZSTK_RUN`. This allows planners to preview without receiving permission to replace persisted plans or access unrelated inventory scopes.

Priority maintenance uses authorization object `ZSTK_PRI`: activity `02` saves a priority and activity `06` removes one, both restricted by plant (`WERKS`) and storage location (`LGORT`). Successful changes retain their scope lock until the report commits. Every save and removal is recorded under application-log subobject `PRIORITY`, preserving deletion history after the current priority row is gone.

The allocation report starts in simulation mode. Leave `P_SIM` selected to calculate and display a fresh plan—including the selected reserve buffer—without enqueueing, logging, persisting, or committing. Clear it only when the displayed scope should replace the saved allocation plan; successful execution prints the newly assigned version, while preview plans remain version zero. `P_NOTE` can attach up to 60 characters of operator rationale to the current header, immutable history header, BAL evidence, catalog, and checked readback. For guarded execution, set `P_EXPECT` to the current version the planner reviewed; under the scope lock, persistence rejects the run without changing current or historical rows if that version is no longer current. For a scope expected to have no saved plan, select `P_NEW`; it rejects execution if another session created the first version. `P_NEW` and a positive `P_EXPECT` are mutually exclusive, while zero with `P_NEW` clear retains unconditional replacement behavior. Report `ZSTOCK_PLAN_VIEW` reads committed headers and details without recalculation, requires display activity `03`, reports a persisted empty plan distinctly from a never-planned scope, and rejects inconsistent stored header/detail data. Select `P_LIST` to show historical versions with provenance, stock context, and header-level requested, allocated, shortage, full, partial, and unallocated KPIs without loading details. Each page is bounded by `P_LIMIT` from 1 to 100; set `P_BEFORE` to the last version shown to retrieve the next older page, optionally restrict creation dates inclusively with `P_HFROM` and `P_HTO`, and select `P_SHORT` to return only versions with shortage. Leave `P_VERSN` at zero for the current snapshot or enter a positive immutable version number from that catalog for historical evidence. Its non-negative `P_MAXAGE` threshold defaults to one day; older valid plans remain visible but carry an explicit stale warning and age in days. Select `P_LIVE` to compare the chosen saved version with one fresh, side-effect-free plan using its strategy, reserve, and window; alternatively, enter another positive saved version in `P_AGNST` to compare two immutable commits. These comparison modes are mutually exclusive. Drift severity is `N` (none), `S` (stock/context only), `D` (demand topology/input), or `O` (allocation outcome); output includes total allocated/shortage deltas and saved/current quantities for every affected key.

Execution summaries are stored under application-log object `ZSTOCKALLOC`, subobject `RUN`. Under the scope lock, a mutation-free preparation step determines the exact next plan version; BAL records that version before persistence, and the sink independently rechecks it while saving. Checked context, quantity, and KPI messages include version, observed stock, allocatable stock, reserve, demand, allocation, shortage quantity, affected-demand count, earliest shortage date, unused stock, fill, service, utilization, fairness, unit, and optional execution rationale even when no demand rows exist. Splitting the summary keeps each entry readable within SAP BAL text limits. A failure adding any message or saving the log aborts allocation persistence, ensuring a committed plan always has a complete audit entry. Current allocation rows also retain their creation date, time, and SAP user; priority rows retain corresponding change metadata. View log entries with the target system's application-log viewer (commonly transaction `SLG1`).

History catalog filters can also select an exact allocation strategy with `P_HSTRAT` and an exact creating SAP user with `P_HUSER`. Date, shortage, strategy, and creator filters all execute before descending version ordering and bounded pagination. Before catalog metadata is exposed, the query boundary validates version order, stock/reserve arithmetic, unit, strategy, planning window, creator provenance, and outcome totals; detailed reads enforce the same provenance requirement.

## Install in SAP

Clone the repository with abapGit. Its configuration imports only `/src/`; `sap_stubs` remains outside the SAP source folder because those definitions model SAP-standard objects only for local linting/transpilation. Confirm the standard `MARD` and `VBBE` fields in the target release, activate `ZSTOCKPLAN`, `ZSTOCKALLOC`, `ZSTOCKPHIST`, `ZSTOCKAHIST`, `ZSTOCKPRIO`, authorization class `ZSTK`, authorization objects `ZSTK_RUN` and `ZSTK_PRI`, and application-log object `ZSTOCKALLOC`, assign the plant/storage-scoped authorizations, and perform a target-system integration test before scheduling productive runs.

## Target-system verification

1. Activate every `/src/` object and confirm the custom table key data elements match the target release's material and sales-document definitions.
2. Test a display-only role (`ZSTK_RUN`, activity `03`) and prove it can simulate and run `ZSTOCK_PLAN_VIEW` only for its assigned plant/storage scopes and cannot execute.
3. Test execute (`16`) and priority change/delete (`02`/`06`) roles against both allowed and denied storage locations.
4. Start overlapping allocation and priority sessions: the same scope must conflict, while a different material/plant/storage scope must proceed.
5. Compare `F`, `P`, `E`, `S`, and `C` simulations for one constrained priority tier, verify `P_OBJ` recommendations for service, quantity, fairness, and due-date urgency goals, test blank, lower-only, upper-only, and bounded `P_FROM`/`P_CUTOF` windows, then reconcile each calculation with `MARD-LABST`, `MARA-MEINS`, and the selected positive `VBBE-OMENG` schedule lines.
6. Verify `RUN` and `PRIORITY` entries in the application-log viewer, including warning severity for shortages and retained history after priority deletion.
7. Force a reversible failure before commit and confirm allocation rows, priority changes, and BAL entries roll back together; then verify successful synchronous commits release their locks.

## Local verification

Requirements: Node.js and npm.

```text
npm install
npm test
```

Both tool configurations load `open-abap/open-abap-core`. The lint configuration includes `src` and `sap_stubs` and enables all rules required by [PLAN.md](PLAN.md). `npm test` first verifies these repository invariants and rejects SAP-standard table writes from custom ABAP. The transpiler then initializes an ephemeral SQLite database from the generated DDIC schema, allowing ABAP Unit to exercise the productive Open SQL readers and custom-table writers as well as the pure allocation logic.

Implementation decisions and follow-up increments are in [NOTES.md](NOTES.md); confirmed defects and tooling limitations belong in [ANOMALIES.md](ANOMALIES.md).
