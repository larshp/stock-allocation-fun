# Stock allocation fun

An ABAP stock allocation vertical slice for an existing SAP system.

Current additions include adaptive strategy `A` (priority when all demand fits, fair-share when stock is scarce) and weighted fair-share strategy `W` (priority-weighted scarce-stock distribution), plus adaptive per-strategy analytics in history/result summaries and dedicated weighted metrics in audit, allocation, health, history, and result summaries. Current history summary schema is `43`, result summary schema is `43`; strategy filters accept `E` (fair-share), `A` (adaptive), and `W` (weighted fair-share). Result summaries expose the exact-run `adaptive_branch` as `priority`, `fair-share`, or `n/a` when originating audit context is unavailable or non-adaptive.

Adaptive allocation summaries and history summaries expose `adaptive_priority_runs`/`adaptive_fair_runs`, derived from each adaptive run's available-versus-requested quantities, so operators can see which branch the policy selected. Allocation success exports use schema `34`; history summary exports use schema `43`.

The current branch provides selectable deterministic priority, FIFO, full-only, smallest-demand-first, largest-demand-first, best-fit, fair-share, and priority-weighted fair-share allocation with explicit full/partial/unallocated line status, preserved SAP sales-document/type/item/schedule-line keys, material-unit conversion for both demand and available stock, audited stock reads and conversions, audited allocation-calculation, snapshot-read, lock-acquisition, and audit-finalization failures, explicit material-existence and base-unit validation, SAP demand-unit validation, filtering of header- and item-delivery-blocked sales orders, rejection auditing for SAP demand-source validation failures, injectable SAP reservation and goods-movement authorization boundaries using `M_MRES_BWA`/`M_MRES_WWA` (reservation type/plant create/delete) and `M_MSEG_BWA`/`M_MSEG_WWA`/`M_MSEG_LGO` (goods-movement type/plant/storage) for both the allocation service and direct BAPI adapters, serialized allocation through an injected SAP enqueue/dequeue boundary, an explicit injectable allocation transaction boundary for replacement and retention writes, a report preview mode that calculates and audits outcomes without reservations or snapshot writes, rejection audit rows for pre-side-effect validation failures, unit-scoped audit history, strategy filtering and per-strategy summaries, dedicated weighted run and quantity/coverage analytics, and retention that removes linked allocation snapshots, optional batch-scoped stock and allocation snapshots through MCHB with required-batch, batch-existence, shelf-life, minimum remaining shelf-life, restricted-status, and delivery-date compatibility validation from MARA/MCHA, SAP-facing MARD/MARA and sales-order readers (VBAP/VBEP/VBAK), per-demand reservation posting through `BAPI_RESERVATION_CREATE1` plus `BAPI_TRANSACTION_COMMIT` with preserved BAPI rejection text, explicit goods-issue and sales-order schedule-line write boundaries through `BAPI_GOODSMVT_CREATE` and `BAPI_SALESORDER_CHANGE`, compensating reservation deletion on partial failure, reservation-document persistence with audit-run and and explicitly retainable run-level audit history in `ZSTOCKALLOC_RUN` including the configured allocation unit and strategy, and a custom `ZSTOCKALLOC` result table. SAP-standard table and API test stubs are kept in `sap_stubs/`; application objects beginning with `Z` are kept in `src/`.

`ZSTOCK_ALLOC_HEALTH` provides a read-only health view for a material/plant/storage-location scope. It classifies the scope as `HEALTHY`, `WARNING`, or `CRITICAL`, emits a stable `reason_code` (`NO_RUNS`, `ERROR_OR_STALE`, `THRESHOLD_BREACH`, `BACKLOG`, or `HEALTHY`), detects stale running work, reports fair-share, weighted fair-share, and adaptive metrics including adaptive priority/fair-share branch counts, accepts optional `p_strat` strategy scoping, `p_stat` audit-lifecycle scoping (`R`, `S`, `P`, or `E`), `p_msg` for a case-insensitive diagnostic-message substring, `p_monly` for nonblank diagnostics only, `p_dfrom`/`p_dto` for inclusive originating demand-count bounds, `p_avf`/`p_avt` for inclusive persisted available-stock bounds, `p_qf`/`p_qt` for inclusive persisted requested-quantity bounds, `p_af`/`p_at` for inclusive persisted allocated-quantity bounds, `p_shf`/`p_sht` for inclusive persisted shortage-quantity bounds, `p_spf`/`p_spt` for inclusive persisted shortage-percentage bounds from 0 through 100, or `p_legacy` to select blank-strategy legacy runs, and accepts `p_ovrd` to retain only runs whose effective requested deadline (`requested_on_to`, falling back to `requested_on_from`) is before the selected as-of date. `p_odate` supplies that overdue as-of date and defaults to the SAP system date when overdue filtering is enabled; it requires `p_ovrd`. `p_dead` retains only runs with an effective requested deadline, while `p_deadf`/`p_deadt` select an inclusive effective deadline range; `p_dagef`/`p_daget` select an inclusive signed deadline-age range where positive values are overdue days and negative values are days remaining, and `p_daged` overrides the age reference date (otherwise the SAP system date is used). Age bounds require a valid range and `p_daged` requires an age bound; these filters can be combined with overdue filtering. The report also accepts `p_cov` as a minimum coverage threshold and `p_spct` as a maximum shortage-percentage warning threshold (`0` disables either threshold); `p_spf`/`p_spt` are independent population bounds. `p_legacy` cannot be combined with `p_strat`. Breaches are exposed as `coverage_below_threshold` and `shortage_above_threshold` in JSON/CSV and change the status to `WARNING` unless errors or stale work make it `CRITICAL`. Health JSON/CSV exports use schema `23` and expose filter provenance including `status_filter`, `message_filter`, `message_only`, `minimum_demand_count`, `maximum_demand_count`, `minimum_available_stock`, `maximum_available_stock`, `minimum_requested_quantity`, `maximum_requested_quantity`, `minimum_allocated_quantity`, `maximum_allocated_quantity`, `minimum_shortage_quantity`, `maximum_shortage_quantity`, `minimum_shortage_pct`, and `maximum_shortage_pct`, plus the selected population’s `deadline_count`, earliest/latest effective deadlines, signed last/oldest/newest deadline ages, and `deadline_age_reference_date`; mixed-unit quantities remain unavailable rather than being summed.

The service validates injected provider and allocator postconditions before side effects, preserves demand identity and source metadata, rejects inconsistent or stale snapshot reservation metadata, preflights cancellation authority for legacy reservations, and persists replacement snapshots before canceling superseded reservations. Cleanup uncertainty is recorded as a partial run with the actionable diagnostic; failed persistence leaves the prior snapshot/reservation pair untouched.

The SAP stock adapter treats a batch master present in `MCHA` but without a storage-stock row in `MCHB` as a valid zero-stock batch, while rejecting material, storage-stock, batch-stock, and batch-master records marked for deletion (`LVORM = X`) rather than allocating from data pending removal.

The SAP order reader excludes rejected, deleted (`VBAP-LOEKZ`), header-delivery-blocked, and item-delivery-blocked sales-order items before mapping open schedule-line demand.

Snapshot persistence and reads verify that the supplied run ID exists in `ZSTOCKALLOC_RUN`, has a recognized lifecycle status and strategy (while preserving blank legacy strategy rows), belongs to the same material/plant/storage/batch/unit scope, and—when the run stores a requested-delivery window—contains demand dates inside that window. Snapshot writes normalize blank payload run and allocation-unit fields to the requested scope and reject conflicting nonblank values, including a payload strategy that disagrees with the run. Writes additionally require the run to be active, while reads accept any legitimate lifecycle status so operators can inspect finalized results. Direct result writers cannot create orphaned snapshots, and result readers cannot silently consume orphaned, malformed, or cross-scope rows.
