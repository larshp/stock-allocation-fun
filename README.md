# Stock allocation fun

An ABAP stock allocation vertical slice for an existing SAP system.

The current branch provides selectable deterministic priority, FIFO, full-only, smallest-demand-first, largest-demand-first, and best-fit allocation with explicit full/partial/unallocated line status, preserved SAP sales-document/type/item/schedule-line keys, material-unit conversion for both demand and available stock, audited stock reads and conversions, audited allocation-calculation, snapshot-read, lock-acquisition, and audit-finalization failures, explicit material-existence and base-unit validation, SAP demand-unit validation, filtering of header- and item-delivery-blocked sales orders, rejection auditing for SAP demand-source validation failures, injectable SAP reservation and goods-movement authorization boundaries using `M_MRES_BWA`/`M_MRES_WWA` (reservation type/plant create/delete) and `M_MSEG_BWA`/`M_MSEG_WWA`/`M_MSEG_LGO` (goods-movement type/plant/storage) for both the allocation service and direct BAPI adapters, serialized allocation through an injected SAP enqueue/dequeue boundary, an explicit injectable allocation transaction boundary for replacement and retention writes, a report preview mode that calculates and audits outcomes without reservations or snapshot writes, rejection audit rows for pre-side-effect validation failures, unit-scoped audit history, strategy filtering and per-strategy summaries, and retention that removes linked allocation snapshots, optional batch-scoped stock and allocation snapshots through MCHB with required-batch, batch-existence, shelf-life, minimum remaining shelf-life, restricted-status, and delivery-date compatibility validation from MARA/MCHA, SAP-facing MARD/MARA and sales-order readers (VBAP/VBEP/VBAK), per-demand reservation posting through `BAPI_RESERVATION_CREATE1` plus `BAPI_TRANSACTION_COMMIT` with preserved BAPI rejection text, explicit goods-issue and sales-order schedule-line write boundaries through `BAPI_GOODSMVT_CREATE` and `BAPI_SALESORDER_CHANGE`, compensating reservation deletion on partial failure, reservation-document persistence with audit-run and allocation-unit correlation, unit-keyed `ZSTOCKALLOC` snapshots that preserve parallel allocations in different units while reconciling active cross-unit reservations against shared stock, queryable and explicitly retainable run-level audit history in `ZSTOCKALLOC_RUN` including the configured allocation unit and strategy, and a custom `ZSTOCKALLOC` result table. SAP-standard table and API test stubs are kept in `sap_stubs/`; application objects beginning with `Z` are kept in `src/`.

The service validates injected provider and allocator postconditions before side effects, preserves demand identity and source metadata, rejects inconsistent or stale snapshot reservation metadata, preflights cancellation authority for legacy reservations, and persists replacement snapshots before canceling superseded reservations. Cleanup uncertainty is recorded as a partial run with the actionable diagnostic; failed persistence leaves the prior snapshot/reservation pair untouched.

The SAP stock adapter rejects material, storage-stock, batch-stock, and batch-master records marked for deletion (`LVORM = X`) rather than allocating from data pending removal.

Snapshot persistence and reads verify that the supplied run ID exists in `ZSTOCKALLOC_RUN`, has a recognized lifecycle status and strategy (while preserving blank legacy strategy rows), belongs to the same material/plant/storage/batch/unit scope, and—when the run stores a requested-delivery window—contains demand dates inside that window. Snapshot writes normalize blank payload run and allocation-unit fields to the requested scope and reject conflicting nonblank values, including a payload strategy that disagrees with the run. Writes additionally require the run to be active, while reads accept any legitimate lifecycle status so operators can inspect finalized results. Direct result writers cannot create orphaned snapshots, and result readers cannot silently consume orphaned, malformed, or cross-scope rows.

```text
npm test
npm run verify
```

Comparison reconciliation now also checks the persisted audit run's requested total and validates each snapshot row's unit and quantity/status relationship. Contextual comparison exports expose `old_snapshot_requested` and `new_snapshot_requested` beside the snapshot row counts, so unit drift, requested-quantity drift, and malformed snapshot lines are distinguishable from allocated or shortage drift.

`p_shrt` sorts comparison rows by highest applicable shortage first. Added and changed rows use the new snapshot shortage; removed rows use the old shortage. Equal shortages use requested date, change type, allocation unit, and order ID tie-breakers, and pagination is applied after this sort. This introduced the comparison `sort_mode` contract, now at schema `53` after the due-date, coverage, shortage-worsening, coverage-deterioration, shortage-percentage-deterioration, requested-quantity-delta, derived-reason, relative-shortage, row-metric, percentage-delta, and summary-metric extensions below.

`p_wors` sorts comparison rows by the largest shortage increase (`new_shortage - old_shortage`) first. Added and changed rows use new shortage values, removals use their old shortage as the last-known value, and improvements or unchanged rows naturally fall after worsening rows. Current shortage, requested date, change type, allocation unit, and order ID provide deterministic ties; pagination is applied after sorting.

`p_cw` sorts comparison rows by the largest allocation-coverage deterioration (`old_coverage_pct - new_coverage_pct`) first. Both snapshot sides must have positive requested quantities for a deterioration value; added, removed, and otherwise non-comparable rows sort after applicable changes. Lower current coverage, shortage, requested date, change type, allocation unit, and order ID provide deterministic ties. `p_wors` takes precedence over `p_cw`, which takes precedence over `p_spw`, `p_qd`, `p_cov`, `p_spct`, `p_due`, and `p_shrt`.

`p_spw` sorts comparison rows by the largest shortage-percentage deterioration (`new_shortage_pct - old_shortage_pct`) first. Both snapshot sides must have positive requested quantities; non-comparable added, removed, or zero-request rows sort last. Current shortage percentage, absolute shortage, requested date, change type, allocation unit, and order ID provide deterministic ties. Sort precedence is `p_wors`, `p_cw`, `p_spw`, `p_cov`, `p_spct`, `p_due`, then `p_shrt`.

`p_qd` sorts comparison rows by descending requested-quantity delta (`new_requested - old_requested`). Added rows therefore sort by their positive new demand, removed rows by their negative old demand, and unchanged rows at zero; current requested quantity, shortage, requested date, change type, allocation unit, and order ID provide deterministic ties. Sort precedence is `p_wors`, `p_cw`, `p_spw`, `p_qd`, `p_cov`, `p_spct`, `p_due`, then `p_shrt`.

Comparison `change_reasons` now include `coverage` when the zero-safe allocated/requested coverage ratio changes or becomes applicable/unavailable, and `shortage_pct` when the corresponding shortage/requested ratio changes; `p_reason=coverage` and `p_reason=shortage_pct` filter to those rows.

`p_due` sorts comparison rows by the earliest available requested date, using the new snapshot for added/changed rows and the old snapshot for removals. Rows without a requested date sort last; shortage, change type, allocation unit, and order ID provide deterministic ties. `p_due` takes precedence over `p_shrt` when both are selected; it introduced schema `42` before the current coverage extension.

`p_cov` sorts comparison rows by lowest applicable allocation coverage first, using the current snapshot for added/changed rows and the old snapshot for removals. Zero-request rows, whose coverage is not applicable, sort last; shortage, requested date, change type, allocation unit, and order ID provide deterministic ties. Sort precedence is `p_wors`, `p_cw`, `p_spw`, `p_qd`, `p_cov`, `p_spct`, `p_due`, then `p_shrt`, and comparison contextual CSV/JSON schema is now `53`.

`p_spct` sorts comparison rows by highest applicable shortage percentage first, using the current snapshot for added/changed rows and the old snapshot for removals. Zero-request rows sort last; absolute shortage, requested date, change type, allocation unit, and order ID provide deterministic ties. Sort precedence is `p_wors`, `p_cov`, `p_spct`, `p_due`, then `p_shrt`.

Result `p_dage` orders rows by the persisted originating-run effective deadline: most overdue signed ages first, then deadline date, shortage, requested date, allocation unit, priority, run ID, and order ID; rows without an effective deadline remain last. Sort precedence is `p_pri`, `p_sstat`, `p_cov`, `p_spct`, `p_dage`, `p_big`, `p_done`, `p_date`, `p_rdate`, then `p_shrt`.
