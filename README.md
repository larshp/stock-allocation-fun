# Stock allocation fun

An ABAP stock allocation vertical slice for an existing SAP system.

The current branch provides selectable deterministic priority, FIFO, full-only, smallest-demand-first, largest-demand-first, and best-fit allocation with explicit full/partial/unallocated line status, preserved SAP sales-document/type/item/schedule-line keys, material-unit conversion for both demand and available stock, audited stock reads and conversions, audited allocation-calculation, snapshot-read, lock-acquisition, and audit-finalization failures, explicit material-existence and base-unit validation, SAP demand-unit validation, filtering of header- and item-delivery-blocked sales orders, rejection auditing for SAP demand-source validation failures, injectable SAP reservation and goods-movement authorization boundaries using `M_MRES_BWA`/`M_MRES_WWA` (reservation type/plant create/delete) and `M_MSEG_BWA`/`M_MSEG_WWA`/`M_MSEG_LGO` (goods-movement type/plant/storage) for both the allocation service and direct BAPI adapters, serialized allocation through an injected SAP enqueue/dequeue boundary, an explicit injectable allocation transaction boundary for replacement and retention writes, a report preview mode that calculates and audits outcomes without reservations or snapshot writes, rejection audit rows for pre-side-effect validation failures, unit-scoped audit history, strategy filtering and per-strategy summaries, and retention that removes linked allocation snapshots, optional batch-scoped stock and allocation snapshots through MCHB with required-batch, batch-existence, shelf-life, minimum remaining shelf-life, restricted-status, and delivery-date compatibility validation from MARA/MCHA, SAP-facing MARD/MARA and sales-order readers (VBAP/VBEP/VBAK), per-demand reservation posting through `BAPI_RESERVATION_CREATE1` plus `BAPI_TRANSACTION_COMMIT` with preserved BAPI rejection text, explicit goods-issue and sales-order schedule-line write boundaries through `BAPI_GOODSMVT_CREATE` and `BAPI_SALESORDER_CHANGE`, compensating reservation deletion on partial failure, reservation-document persistence with audit-run and allocation-unit correlation, unit-keyed `ZSTOCKALLOC` snapshots that preserve parallel allocations in different units while reconciling active cross-unit reservations against shared stock, queryable and explicitly retainable run-level audit history in `ZSTOCKALLOC_RUN` including the configured allocation unit and strategy, and a custom `ZSTOCKALLOC` result table. SAP-standard table and API test stubs are kept in `sap_stubs/`; application objects beginning with `Z` are kept in `src/`.

The service validates injected provider and allocator postconditions before side effects, preserves demand identity and source metadata, rejects inconsistent or stale snapshot reservation metadata, preflights cancellation authority for legacy reservations, and persists replacement snapshots before canceling superseded reservations. Cleanup uncertainty is recorded as a partial run with the actionable diagnostic; failed persistence leaves the prior snapshot/reservation pair untouched.

Snapshot persistence and reads verify that the supplied run ID exists in `ZSTOCKALLOC_RUN`, has a recognized lifecycle status, and belongs to the same material/plant/storage/batch/unit scope. Writes additionally require the run to be active, while reads accept any legitimate lifecycle status so operators can inspect finalized results. Direct result writers cannot create orphaned snapshots, and result readers cannot silently consume orphaned, malformed, or cross-scope rows.

Run the checks with:

```text
npm test
npm run verify
```

`npm test` transpiles and runs the generated ABAP Unit harness. `npm run verify` adds the lint pass. Open ABAP Core is pinned by commit as an npm development dependency; lint and transpilation use its installed local folder, so checks do not require a fresh GitHub clone after `npm install`. The transpiler emits the ABAP Unit runner into `output/`.

The allocation, history, and result reports require `S_TABU_NAM` read authorization for the audit or result table they query and report missing authorization cleanly. Allocation execution additionally requires activity `02` write authorization for `ZSTOCKALLOC_RUN` audit rows, activity `02` change authorization for `ZSTOCKALLOC` result rows, and activity `06` delete authorization for snapshot replacement; purge enforces activity `06` retention authorization for both affected tables at the API boundary. The concrete SAP adapters also default to their standard authorization ports when called directly without dependency injection, so callers cannot bypass these checks by omitting an optional port.

The read-only `ZSTOCK_ALLOC_HISTORY` report lists the scoped run ID, status, unit, persisted strategy, requested-delivery window, available stock, demand count, allocated quantity, shortage, start and finish timestamps, elapsed duration in seconds, and diagnostic message for operational review; running rows have no finish timestamp or duration. It prints lifecycle, quantity, allocation coverage percentage, full/partial/unallocated demand totals, and per-strategy run counts for the filtered population before the detail rows, omitting quantity aggregation when the rows use different units. `p_runid` optionally selects one exact audit run, while `p_reqf` and `p_until` filter the output to one persisted requested-delivery window; reversed horizon bounds are rejected. `p_stat` accepts `R`, `S`, `P`, or `E`, and `p_strat` accepts `P`, `F`, `N`, `S`, `L`, or `B`; `p_from` and `p_to` optionally filter the output by run-start date, `p_ffrom`/`p_fto` optionally filter by finish date, `p_shf`/`p_sht` optionally filter by inclusive shortage range, `p_af`/`p_at` optionally filter by inclusive allocated-quantity range, `p_avf`/`p_avt` optionally filter by inclusive available-stock range, `p_qf`/`p_qt` optionally filter by inclusive derived requested-quantity range (`allocated + shortage`), `p_dfrom`/`p_dto` optionally filter by inclusive demand-count range, `p_covf`/`p_covt` optionally filter by inclusive allocation-coverage percentage from 0 to 100, and `p_spf`/`p_spt` optionally filter by inclusive shortage percentage from 0 to 100. Runs with zero requested quantity are excluded when a coverage or shortage-percentage bound is supplied because the ratio is not applicable. Selecting `p_shrt` orders history by descending shortage, then start chronology and run ID; without it, the default newest-started-first order is retained. Requesting a finish window excludes still-running rows. History read failures are reported cleanly. Direct summaries without a unit remain safe across parallel units: `mixed_units` is set and aggregate requested/allocated/shortage quantities are blank when runs use different units. The audit summary API exposes `requested` explicitly as allocated plus shortage for unit-consistent populations.

`p_tfrom`/`p_tto` optionally filter completed history rows by inclusive elapsed duration in seconds; running rows are excluded whenever a duration bound is requested, and negative or reversed bounds are rejected.

Selecting `p_tdur` orders history by elapsed duration descending, with start timestamp and run ID as deterministic tie-breakers. Coverage-first ordering takes precedence, followed by duration-first and then shortage-first ordering.

Selecting history `p_sstat` orders runs by diagnostic risk: errors, partial runs, running runs, then successes; shortage and newest-start tie-breakers remain deterministic. Coverage-first ordering takes precedence, followed by status-first, duration-first, and shortage-first ordering.

`p_stale` optionally keeps only running audit rows whose elapsed age is at least the supplied number of seconds; negative thresholds are rejected. This is independent of finalized-run duration filtering. Audit finalization rejects partial (`P`) runs with zero shortage so lifecycle status and metrics remain consistent.

`ZSTOCK_ALLOC_WATCH` is a focused operational view for stale active runs. It accepts the same material/plant/storage-location scope, optional batch and unit, optional exact `p_runid`, an optional case-insensitive diagnostic-message substring `p_msg`, `p_monly` to retain only runs with a diagnostic message, an optional `p_strat` filter (`P`, `F`, `N`, `S`, `L`, or `B`), an optional nonnegative `p_shf` minimum-shortage filter, optional `p_covf` and `p_covt` minimum/maximum coverage filters from 0 to 100, a nonnegative `p_stale` threshold (default 3600 seconds), an optional nonnegative `p_age_to` maximum running-age bound, an optional nonnegative `p_skip` offset, an optional `p_max` alert limit, `p_shrt` to sort by shortage, `p_cov` to sort by lowest applicable coverage first, and `p_new` to sort newest-started stale runs first. When multiple sort checkboxes are selected, coverage sorting takes precedence over shortage, which takes precedence over newest-first; each mode retains deterministic age/time/run-ID ties. When both coverage bounds are supplied, the minimum must not exceed the maximum; when `p_age_to` is supplied, it must not be below `p_stale`. Alerts are calculated through the canonical running-age API; the default is oldest-first. Human, CSV, and JSON output are supported; JSON uses schema version `18` and includes `sort_mode`, filter provenance including `message_filter`, `message_only`, `minimum_coverage`, `maximum_coverage`, and `maximum_age_seconds`, `offset`, `has_more`, pre-limit `candidate_count`, a boolean `limited` truncation marker, returned `alert_count`, quantity/coverage aggregates, and oldest/newest alert age (`null` when unavailable). Returned detail alerts include a one-based stable global `rank` after sorting and typed `coverage_pct` (`null` for zero-request runs). Selecting `p_ndjson` with `p_json` emits one complete self-describing alert object per line, repeats the filter and page context on each line, emits no array delimiters, and is mutually exclusive with `p_sum`; an empty feed emits no data lines. Detail CSV uses schema version `18`; selecting `p_sum` suppresses alert rows in human, CSV, and JSON output, leaving only the aggregate summary; summary CSV also uses schema version `18`. Blank filters are reported as `n/a`. Zero-request runs are excluded when a coverage bound is supplied because coverage is not applicable.

The read-only `ZSTOCK_ALLOC_RESULT` report displays the scoped per-demand allocation status, requested delivery date, normalized allocation unit, original sales-order unit, requested/allocated/shortage quantities, sales-document type, reservation ID and lifecycle metadata (date, movement type, and unit), and audit run ID from `ZSTOCKALLOC`.

The read-only `ZSTOCK_ALLOC_COMPARE` report compares two persisted allocation runs for one material/plant/storage-location scope. `p_old` and `p_new` identify the runs; `p_meins` optionally narrows the comparison to one allocation unit, and `p_charg` retains batch scope. By default it emits only changed demand keys: `A` means added in the new run, `R` means removed, and `C` means the key exists in both runs but its persisted source identity, allocation strategy, requested date, priority, status, quantities, reservation ID, or reservation metadata changed. Every detail row also carries deterministic pipe-delimited `change_reasons` (`added`, `removed`, or the changed field names). `p_reason` filters to one validated reason such as `reservation_id`, `allocated`, `sales_document`, or `allocation_strategy`; `p_all` includes unchanged keys as `U` with an empty reason list. CSV and JSON detail rows expose old/new source-document, schedule-line, order-unit, and reservation metadata alongside the existing quantity/delta fields, while `p_typed` emits numeric priorities and quantities. `p_chg` restricts output to one change type, while `p_skip` and `p_max` provide offset/limit pagination; `p_meta` wraps JSON rows with `total_rows`, `offset`, `max_rows`, `old_run`, `new_run`, `change_type`, `reason_filter`, `include_unchanged`, authorized old/new lifecycle status, strategy, timestamps, requested-delivery horizons, available-stock baselines, and messages, plus `old_reconciliation`/`new_reconciliation` and snapshot-row counts so consumers can distinguish the filtered total from the returned page and verify each snapshot against its audit counters and quantities. `p_guard` makes that check strict and returns an error instead of comparison output when either run is inconsistent. CSV and human output expose the same old/new run and reconciliation context; plain JSON arrays and NDJSON retain their existing row-only shape. `p_sum` emits aggregate counts and old/new/delta requested, allocated, and shortage quantities; its totals are calculated before pagination, and it works in human, CSV, and JSON modes (with `p_meta`, JSON nests the summary beside the comparison page context). When a comparison spans multiple allocation units, summary quantity totals are suppressed as non-comparable, with `mixed_units` exposed and `n/a`/`null` output as appropriate. `p_ndjson` streams one complete comparison row object per line for large consumers, preserves regular or typed row encoding, requires JSON, and cannot be combined with `p_meta` or `p_sum`. Comparison reads use the existing result-read authorization boundary and reject duplicate snapshot keys or identical old/new run IDs.

When `p_meins` is blank, parallel result snapshots in all allocation units are displayed together. `p_runid` restricts output to one persisted audit run and prints that run’s lifecycle context, audit counters, and diagnostic message, even when the run has no snapshot rows yet. When `p_runid` is the only detail filter, the report also reconciles snapshot line/outcome counts and allocated/shortage quantities against the audit row and prints `OK` or `MISMATCH`; filtered views intentionally omit that comparison. `p_stat` accepts `F`, `P`, and `U` to show only fully allocated, partially allocated, or unallocated result lines, `p_vbeln` selects the persisted sales document, `p_auart` selects its document type, `p_posnr` selects its item, `p_etenr` selects its schedule line, `p_ounit` selects the original sales-order unit, `p_order` selects one derived demand key, `p_resid` selects a SAP reservation document, `p_rmov` selects a reservation movement type, `p_runit` selects the persisted reservation unit, `p_rsv` keeps only rows with a reservation ID, `p_rfrom`/`p_rto` select an inclusive reservation-posting-date window, `p_from`/`p_to` select an inclusive requested-delivery-date window, `p_priof`/`p_priot` select an inclusive allocator-priority range, `p_shf`/`p_sht` select an inclusive shortage-quantity range, `p_qf`/`p_qt` select an inclusive requested-quantity range, `p_af`/`p_at` select an inclusive allocated-quantity range, and `p_spf`/`p_spt` select an inclusive shortage-percentage range from 0 to 100. Selecting `p_pri` orders rows by allocation unit, persisted priority, and order key; selecting `p_sstat` orders unallocated rows first, then partial and full rows, followed by shortage/date/unit/priority/order-key tie-breakers; selecting `p_cov` orders by ascending coverage; selecting `p_spct` orders by descending shortage percentage, then shortage, requested date, allocation unit, priority, and order key; selecting `p_big` orders by descending requested quantity; selecting `p_done` orders by descending allocated quantity; selecting `p_date` orders globally by requested delivery date; selecting `p_rdate` orders by reservation date; and selecting `p_shrt` orders by descending shortage. Sort precedence is `p_pri`, `p_sstat`, `p_cov`, `p_spct`, `p_big`, `p_done`, `p_date`, `p_rdate`, then `p_shrt`. The report prints unit-safe requested, allocated, shortage, and allocation coverage totals plus the exact order ID and persisted allocation priority for reconciliation.

Comparison reconciliation now also checks the persisted audit run’s requested total. Contextual comparison exports expose `old_snapshot_requested` and `new_snapshot_requested` beside the snapshot row counts, so a requested-quantity drift is distinguishable from allocated or shortage drift.

Exact-run `ZSTOCK_ALLOC_RESULT` reconciliation applies the same requested-total equality in JSON metadata and human output, alongside its existing outcome, allocated, and shortage checks. JSON metadata and human output also expose `reconciliation_fields`, identifying the mismatched audit metrics or the state reason (`not_requested`, `filtered`, or `unavailable`).

Comparison contextual outputs additionally expose old/new snapshot full, partial, and unallocated row counts plus requested, allocated, and shortage totals. Exact-run result metadata and human output expose the corresponding snapshot metrics for direct audit diagnosis.

Comparison summary CSV/JSON and comparison detail CSV/JSON metadata envelopes expose numeric `schema_version: 20`; version 20 adds `audit_running_age_trend` (`older`, `younger`, `unchanged`, or `unavailable`) beside the live `old_running_age_seconds`, `new_running_age_seconds`, and `audit_running_age_delta_seconds` fields introduced in version 19. Typed JSON emits numbers when the corresponding run is active with usable timestamps and `null` otherwise; regular JSON and CSV use numeric text or `n/a`. Version 18 adds `audit_reconciliation_transition`, classified as `both_ok`, `recovered`, `regressed`, `both_mismatch`, or `unavailable`. Version 17's `audit_metadata_change_reasons`, a pipe-delimited list of changed audit metadata categories (`status`, `strategy`, `unit`, `horizon`, `timestamps`, and `message`), version 16's aggregate metadata flag, and version 15's `audit_reconciliation_ok` health flag remain available alongside the reconciliation statuses, transition indicator, outcome-counter deltas, timing deltas, running-state and duration deltas, status/strategy indicators, requested-delivery-horizon changes, unit-safe quantity deltas, and coverage/shortage-percentage deltas. Timing and quantity deltas retain typed `null` and regular `n/a` when their inputs are unavailable or non-comparable. Unit-safe audit coverage and shortage percentages remain available per run, with zero-request runs represented as `null` in typed JSON and `n/a` elsewhere. These complement audit-side outcome counters and requested/allocated/shortage totals alongside persisted start/finish times, generated response date/time, run duration, requested-delivery horizon, and available-stock baseline context. Snapshot-side and audit-side metrics are both available for direct reconciliation diagnosis. Plain JSON arrays and NDJSON remain row-only for backward compatibility.
`p_latest` selects the newest matching audit run automatically and applies that run ID to the result read, JSON metadata, reconciliation, and CSV output. When supplied, `p_from` and `p_to` also constrain the audit match to the requested-delivery horizon, while `p_covf`/`p_covt` and `p_spf`/`p_spt` constrain the aggregate run coverage and shortage-percentage metrics used to select that latest run. It cannot be combined with an explicit `p_runid`; use the exact run ID when a specific historical run is required.

`p_strat` restricts result rows and `p_latest` selection to persisted strategy `P`, `F`, `N`, `S`, `L`, or `B`; `p_legacy` restricts them to blank legacy strategy runs. These strategy filters are mutually exclusive and are included in metadata filter names.

`p_rage` optionally keeps only reserved rows whose reservation date is at least the supplied number of days old; negative ages are rejected and unreserved rows are excluded.

`p_rid` optionally keeps result rows linked to a run ID containing the supplied fragment. It can be combined with an exact `p_runid` for an additional guard, and it is applied when `p_latest` selects the newest matching run.

For any filtered result set, the report prints total lines and counts of fully allocated, partially allocated, and unallocated demands before the detailed rows. It also prints requested/allocated/shortage quantity totals when all rows share one allocation unit; mixed-unit result sets intentionally omit quantity aggregation.

Result-line `p_covf`/`p_covt` filters select inclusive allocation-coverage percentages from 0 to 100, calculated as allocated quantity divided by requested quantity. Lines with zero requested quantity are excluded when coverage bounds are supplied. `p_spf`/`p_spt` apply the complementary shortage-percentage range, calculated as shortage quantity divided by requested quantity; lines with zero requested quantity are excluded when those bounds are supplied. `p_spct` orders rows by descending shortage percentage, then shortage, requested date, allocation unit, priority, and order key.

Selecting result-report `p_cov` orders lines by ascending allocation coverage, then descending shortage, requested date, allocation unit, priority, and order key. Sort precedence is priority (`p_pri`), coverage (`p_cov`), requested date (`p_date`), then shortage (`p_shrt`).

Result-report `p_max` caps the returned rows after filtering and sorting; a positive value is required for a cap, negative values are rejected before the read, and capped exact-run views do not claim full reconciliation. Exact run-ID reads are pushed into the SAP SELECT predicate for a narrower database read.

Result-report `p_skip` skips that many rows after filtering and sorting, before `p_max`; it must be nonnegative, and any nonzero offset disables exact-run reconciliation.

Selecting result-report `p_big` orders by descending requested quantity, then descending shortage, requested date, allocation unit, priority, and order key. Sort precedence is priority, coverage, largest demand (`p_big`), requested date, then shortage.

Selecting `p_done` orders by descending allocated quantity, then requested quantity, shortage, requested date, allocation unit, priority, and order key. It follows `p_big` and precedes requested-date/shortage ordering.

Selecting result-report `p_rdate` orders by reservation date ascending, then allocation unit, priority, and order key; unreserved rows sort first so reservation follow-up is immediately visible. It follows requested-date ordering and precedes shortage ordering.

Smallest-demand-first sorts by requested quantity ascending, then priority, requested date, and order ID; largest-demand-first uses the same deterministic tie-breakers with requested quantity descending.
